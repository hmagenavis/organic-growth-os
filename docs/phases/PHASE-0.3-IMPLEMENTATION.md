# PHASE-0.3 — Authentication & Session Security (implementation record)

Status: **COMPLETE** — 2026-08-31
Scope source: `docs/phases/PHASE-0.md` §0.3 (authentication half only)
Verified against PostgreSQL 16 via Testcontainers. See §14.

Phase 0.3 answers one question: **who is this user, and is this session authentic?**
It deliberately does not answer *what may they do* — that is Phase 0.4. §11 describes
the boundary between the two and the test that holds it in place.

## 2. Password architecture

**Argon2id via `@node-rs/argon2`.** A maintained NAPI-RS binding that ships prebuilt
binaries, so CI (Linux) and development (Windows) run the same implementation without
a native toolchain. No hashing, salting, encoding or comparison is written by hand;
verification uses the library's own constant-time primitive.

**Parameters (production baseline).** `memoryCost = 19456 KiB (19 MiB)`, `timeCost = 2`,
`parallelism = 1` — the first configuration recommended by the OWASP Password Storage
Cheat Sheet for Argon2id. They are defined once, in `DEFAULT_PASSWORD_HASH_PARAMETERS`,
and overridable through `AUTH_ARGON2_*`. A unit test asserts the shipped defaults meet
that floor, so lowering them fails CI rather than passing review as a config tweak.
The environment schema also refuses a memory cost below 8 MiB outright.

**Properties.**

- Only `users.password_hash` is stored; there is no column a plaintext could go in.
- A fresh random salt per hash, generated by the library — two hashes of the same
  password never match.
- `verify()` returns `false` for an absent, empty, foreign or corrupt stored value
  rather than throwing, so a malformed row can never be read as a success.
- `hash()` refuses empty input and anything over 1024 characters; the resulting error
  message never contains the input.
- Passwords never appear in an error, a log line, a response body or a rate-limit key.
- The algorithm identifier is restated locally (`ARGON2ID = 2`) because the library
  declares it as an ambient `const enum` that `isolatedModules` cannot import; a test
  asserts produced hashes really are `$argon2id$`, closing that loop.

**Policy for setting a password** (`checkPasswordPolicy`): minimum 12 characters,
maximum 1024, no composition rules. It is applied where a password is *chosen*, never
at login — the login endpoint must not reveal the policy any more than it reveals
whether an account exists.

## 3. Session token design

```
generateSessionToken()            32 CSPRNG bytes → base64url (43 chars, 256 bits)
        │
        ├─→ browser cookie            (the only place the raw token exists)
        │
        └─→ SHA-256 → sessions.token_hash   (the only place the database sees)
```

SHA-256 rather than a KDF is correct here: unlike a password, the token already
carries full 256-bit entropy, so there is nothing for a slow hash to defend against.

Resolution is `cookie → hash → row lookup → user`. A token that could not have come
from the generator (wrong length or wrong alphabet) is rejected before it becomes a
query parameter. JWTs are not used anywhere (ADR-0013): revocation has to be
immediate, and a denylist is a session table with extra steps.

## 4. Session lifecycle

`sessions` columns after migration 0003: `id`, `user_id`, `token_hash`, `created_at`,
`expires_at`, `last_used_at`, `revoked_at`, `ip`, `user_agent`.

| Policy | Variable | Default |
|---|---|---|
| Absolute lifetime | `AUTH_SESSION_ABSOLUTE_LIFETIME_MS` | 12 h |
| Idle timeout | `AUTH_SESSION_IDLE_TIMEOUT_MS` | 2 h |
| Activity write interval | `AUTH_SESSION_TOUCH_INTERVAL_MS` | 60 s |
| Cleanup grace | `AUTH_SESSION_CLEANUP_GRACE_MS` | 7 days |

Twelve hours is a working day: a console that can push changes to production sites
should ask for the password again the next morning. Both limits are enforced on every
resolution, not only at creation — the absolute cap in SQL (`expires_at > now`), the
idle cap in `SessionService` where the policy lives. Nothing hardcodes a duration
anywhere else in the codebase.

`last_used_at` is written at most once per touch interval, so an active session costs
one UPDATE a minute rather than one per request. An idle-expired session is revoked
eagerly when it is first seen, so it cannot be revived and cleanup can collect it.

**Cleanup** is a command, not a job: `pnpm sessions:cleanup`. It deletes sessions that
finished (revoked or past absolute expiry) longer ago than the grace window, runs as
the ordinary runtime role, is idempotent, and is safe to run concurrently. BullMQ is
sub-phase 0.5; building the queue to run one DELETE would be building it early. The
command is written to be exactly what that scheduler will invoke.

## 5. Session rotation and revocation

Rotation issues a new token and revokes the old one, so the two are never valid
together. It happens today on **successful authentication over an existing session**
(session fixation: the token a caller arrives with is dead afterwards), and
`SessionService.rotateSession` is available for the other cases the design calls for —
password change and privilege/membership change. Those endpoints do not exist yet:
Phase 0.3 exposes no privilege-changing route, by scope.

Revocation primitives:

| Primitive | Used by | Available to |
|---|---|---|
| `revokeByToken` | logout, login rotation | the API |
| `revokeById` | idle expiry | Phase 0.4 administrative force-logout |
| `revokeAllForUser` | — | Phase 0.4 (password change, membership change, admin) |

Revocation is a write (`revoked_at`), not a delete, so a revoked session stays visible
to incident review until cleanup collects it. Deciding *who may invoke* administrative
revocation is authorization, and belongs to Phase 0.4; the persistence primitives are
ready for it.

## 6. Cookie security

Production and development are **separate profiles**, not one profile with a flag
turned down.

| | Production | Local HTTP development |
|---|---|---|
| Session cookie | `__Host-organic-os-session` | `organic-os-dev-session` |
| CSRF cookie | `__Host-organic-os-csrf` | `organic-os-dev-csrf` |
| `Secure` | yes | no |
| `HttpOnly` (session) | yes | yes |
| `SameSite` | `Lax` (configurable to `Strict`) | same |
| `Path` | `/` | `/` |
| `Domain` | never set | never set |
| `Max-Age` | tracks the session's absolute expiry | same |

The `__Host-` prefix means a browser rejects the cookie unless it is `Secure`, has
`Path=/` and carries no `Domain` — which makes it impossible for a sibling subdomain to
overwrite the session. `assertHostPrefixSafe` enforces the same three conditions on our
side, so a misconfiguration throws here instead of being silently discarded by the
browser.

**Production fails closed.** `createAuthConfig` refuses to build with
`NODE_ENV=production` and `AUTH_COOKIE_SECURE=false`, and the API validates it at
startup, before `listen`. Nothing about making localhost work can reach the production
settings, because the development profile is a different cookie with a different name.
A developer running local HTTPS sets `AUTH_COOKIE_SECURE=true` and gets the production
profile exactly.

The CSRF cookie is deliberately **not** `HttpOnly`: the double-submit pattern requires
the page's own script to read it and echo it in a header, which is precisely what a
cross-site request cannot do. It carries a random nonce and a MAC, and nothing else.

Cookie serialization and parsing are implemented in `packages/auth/src/cookies.ts`
rather than taken from a Fastify plugin. Reason: a plugin's cookie-parsing hook is
appended when the plugin loads, which is *after* root-level hooks are registered, so
plugin load order would decide whether the authentication hook can see the session
cookie. Forty lines of well-specified string handling removed that hazard and kept the
auth package framework-free. The parser skips malformed pairs instead of throwing,
keeps the first of a duplicated name (so a later injected duplicate cannot override an
earlier value), and returns a null-prototype object.

## 7. CSRF architecture

**Signed double-submit**, per SECURITY.md §2 and ADR-0013. A request that changes state
is accepted only when all three hold:

1. the CSRF cookie and the `x-csrf-token` header carry the same value (timing-safe);
2. the value's HMAC-SHA256 signature verifies under `AUTH_SESSION_SECRET` — so a token
   cannot be minted by anyone else, which is what an *unsigned* double-submit fails to
   prevent against cookie injection from a sibling subdomain;
3. the signature covers the **binding**: the current session id, or `anonymous` before
   login. A token issued for the attacker's own session does not verify against a
   victim's.

Token shape: `<nonce-base64url>.<hmac-base64url>`. It encodes nothing — not the
binding, not an address, not a session id — and is never persisted.

Enforcement is a root `onRequest` hook covering every non-safe method
(`POST/PUT/PATCH/DELETE`); `GET`, `HEAD`, `OPTIONS` and `TRACE` are untouched. The
session is resolved by an earlier hook so the CSRF check knows the binding.

**Login is not exempt.** Login CSRF is a real attack — it signs a victim into the
attacker's account — and `GET /auth/csrf` makes an anonymous-bound token free to
obtain. The CSRF cookie is reissued whenever the binding changes: on login (bound to
the new session) and on logout (back to `anonymous`).

`SameSite=Lax` is configured on the cookies and treated strictly as defence in depth,
never as the control.

**Known ergonomic cost.** A client holding a session-bound CSRF token whose session has
since expired will get `403` on its next state-changing request, including logout,
because the binding is now `anonymous`. The fix is a `GET /auth/csrf` round trip. This
is accepted rather than papered over: accepting either binding would give back the
fixation resistance that binding buys.

## 8. Login rate limiting

Two budgets, both consumed only on **failed** attempts, checked before any credential
work:

| Budget | Variable | Default | Attack it addresses |
|---|---|---|---|
| Per source address | `AUTH_LOGIN_RATE_LIMIT_IP_MAX` | 20 / 15 min | one origin, many accounts (stuffing) |
| Per account | `AUTH_LOGIN_RATE_LIMIT_ACCOUNT_MAX` | 10 / 15 min | many origins, one account (targeted) |

A success clears the account budget but leaves the source budget counting, so one valid
credential does not buy an unlimited spraying run.

**No existence oracle.** A failed attempt against an address that does not exist
consumes exactly as much account budget as one against an address that does, so the
`429` is identical either way — and the account key is `sha256(normalized email)`, so
the store never holds an address in the clear.

**Source key.** `request.ip`, which is the socket peer because the Fastify app is built
with `trustProxy: false`. It therefore cannot be forged with an `X-Forwarded-For`
header. A deployment behind a proxy must configure `trustProxy` explicitly.

### Current limitation, stated plainly

`InMemoryRateLimitStore` keeps counters in one Node.js process's heap. **With more than
one API instance behind a load balancer an attacker gets the configured budget per
instance, and a restart clears every counter.** It is real protection for a
single-instance deployment and nothing more.

It is not a placeholder — it enforces exactly what it claims — but:

- it sits behind the `RateLimitStore` interface, whose single atomic `hit`
  (increment-and-read within a fixed window) is deliberately shaped so a Redis
  `INCR` + `EXPIRE` implementation can satisfy it with no caller changes;
- `store.distributed` is `false`, so a deployment can *assert* the property rather
  than assume it;
- the API logs a warning at startup in production saying so.

**A multi-instance production deployment must not claim distributed brute-force
protection until sub-phase 0.5 replaces this with a Redis-backed store.** Redis was not
added here because Redis is 0.5's scope and pulling it forward for one counter would
be building infrastructure before the thing that needs it.

## 9. Endpoints

| Route | Auth | CSRF | Behaviour |
|---|---|---|---|
| `GET /auth/csrf` | not required | not checked (safe) | issues a token bound to the caller's current binding, sets the CSRF cookie, returns the token and the header name |
| `POST /auth/login` | not required | **required** | normalize → look up → Argon2id verify → revoke any presented session → create session → set cookies → record login |
| `POST /auth/logout` | optional | required | revokes the current session, clears the cookie, rebinds CSRF to anonymous, always `204` |
| `GET /auth/me` | required | not checked (safe) | `{ id, email, name, locale }` |

`/auth/me` returns identity only. It does **not** report organizations, memberships,
roles, client scopes or `is_platform_admin`. `is_platform_admin` is loaded into the
server-side identity because the schema carries it, but no response body exposes it and
no code path can set it.

Email normalization is trim + lowercase, and nothing more: `users.email` is `citext` so
the database already matches case-insensitively, and this keeps the application's view
consistent so one address cannot be given two rate-limit budgets. Dots and `+tags` are
preserved — stripping them would silently merge addresses that are distinct mailboxes
at most providers.

**One failure response.** Unknown address, no credential set, and wrong password all
produce the same `401` problem+json (`invalid-credentials`, "Email or password is
incorrect."). Internally they are distinguished by a coarse `reason` category for the
log.

**Timing.** When there is no stored hash to verify against, the provided password is
still verified — against a throwaway hash generated at first use with the same cost
parameters — so an unknown address costs the same wall-clock time as a wrong password.

Logout is idempotent: revoking an already-dead or absent session succeeds, and the
cookie is cleared either way.

## 10. Authentication middleware

```
authenticateRequest(request)
  → parse Cookie header
  → SHA-256 the session token
  → find a live session (unrevoked, inside absolute expiry, inside idle window)
  → load the user
  → request.auth = { identity | null, failure category, presented token }
```

`RequestAuthentication` carries a user and a session **and nothing else** — no
organization, no role, no client scope, no tenant context. Per-request state lives in a
`WeakMap` behind a getter/setter decorator rather than on a shared decorator object,
because Fastify v5 rejects reference-typed request decorators for exactly the reason
that matters here: one caller's authentication must never become another's.

## 11. The authentication / tenancy boundary

This is the most important architectural property of the phase.

**Authenticating a user establishes no tenant authority.** Concretely:

- Nothing in the authentication path sets `app.current_org_id`. The settings it does
  use — `app.auth_email`, `app.auth_user_id` — are different settings that no tenant
  policy consults.
- `AuthenticatedIdentity` has no field from which an organization could be read.
- Reaching tenant data still requires an explicitly constructed `TenantContext` passed
  to `withTenantTransaction`, which authentication never supplies.

Proven in `packages/database/src/auth/auth-store.int.test.ts` and
`apps/api/src/auth/auth.int.test.ts`: a user who is a genuine `agency_admin` of
organization A logs in successfully, and the runtime role still reads **zero rows** from
`organizations`, `clients`, `sites`, `memberships`, `site_settings` and `audit_logs`,
and a cross-organization INSERT is refused. Phase 0.4's authorization step is what will
change that.

## 12. Database changes

### Migration `0003_authentication.sql` (forward-only)

**Session lifecycle columns.** `last_used_at timestamptz NOT NULL DEFAULT now()`
(back-filled from `created_at`) and `revoked_at timestamptz`, plus a partial index on
`revoked_at` for the cleanup command. The rest of the Phase 0.2 `sessions` table is
untouched — it was reviewed first and needed no redesign.

**An authentication lookup path on `users`.** Migration 0002 deliberately made `users`
unreadable without a tenant context. Authentication happens *before* any organization
is known: at login there is only an email address. `sessions` was already left outside
RLS for exactly this reason; `users` could not be, because it is also organization
directory data.

The path added is a **point lookup, not an exemption**:

```sql
CREATE POLICY users_authentication_lookup ON users
  FOR SELECT TO organic_os_runtime
  USING (email = app.auth_email() OR id = app.auth_user_id());
```

`app.auth_email()` / `app.auth_user_id()` read transaction-local settings and return
NULL when unset — the same construction as `app.current_org_id()`, so with no context
the predicate is NULL and matches nothing. Because the caller must already supply the
exact address or id, there is **no predicate under which the policy returns more than
one row**: a `SELECT * FROM users` under an authentication context returns exactly the
one user, which the integration suite asserts.

Recording a login needs an UPDATE, and it is scoped twice over:

```sql
CREATE POLICY users_authentication_touch ON users
  FOR UPDATE TO organic_os_runtime
  USING (id = app.auth_user_id()) WITH CHECK (id = app.auth_user_id());

GRANT UPDATE (last_login_at) ON users TO organic_os_runtime;
```

The **column-scoped grant** means the runtime role physically cannot write
`password_hash`, `email` or `is_platform_admin` no matter what SQL it issues — asserted
by tests that expect `permission denied`.

### What was *not* weakened

No `BYPASSRLS`. No role became an object owner. `FORCE ROW LEVEL SECURITY` is unchanged
on every tenant table. The migration role gained no data policy. Provisioning
credentials are not opened by the API process at all. No unscoped tenant repository was
added. Tenant-context semantics are unchanged. All 22 Phase 0.2 tenant-isolation tests
still pass, unmodified.

### `sessions` remains outside RLS — reconfirmed

A session is resolved from a token hash before any organization is known, so a tenant
predicate cannot be evaluated. The table is not a pathway to tenant data, and a test
asserts why: its columns are `id, user_id, token_hash, expires_at, last_used_at,
revoked_at, ip, user_agent, created_at` — there is no `organization_id`, `client_id` or
`site_id`, and nothing joinable to tenant rows without a tenant context that
authentication never establishes.

## 13. Privileged provisioning boundary

No public sign-up or organization-provisioning endpoint exists, and none is reachable
from the API.

The internal service boundary designed for it is `provisionUser`, which now accepts an
optional `passwordHash` (never a plaintext). It runs only on a **provisioning-role**
connection, because the runtime role holds no INSERT grant on `users` and no UPDATE
grant on `password_hash`. The API process opens only the runtime connection — the
provisioning and migration connection strings are never read by it.

Tests seed credentialed users through that same privileged path, which is why no
test-only backdoor exists in application code: the boundary the tests cross is the real
one. Phase 0.4 will design the explicit user → organization → first `agency_admin`
workflow on top of it.

Platform administration: `users.is_platform_admin` is loaded as identity data and
nothing more. No API sets it, no endpoint reports it, and the runtime role's
column-scoped grant makes writing it impossible.

## 15. Deviations from the planning documents

| Deviation | Rationale |
|---|---|
| Cookie name `__Host-organic-os-session`, not SECURITY.md's `__Host-ogos_session` | The project settled on the `organic-os` prefix elsewhere; `ogos` appears nowhere else. Cosmetic, and SECURITY.md §2 is updated. |
| Cookie serialization is implemented here rather than via `@fastify/cookie` | A plugin's cookie-parsing hook loads after root hooks, so plugin ordering would decide whether the authentication hook can see the session cookie. See §6. |
| Authentication env lives in `packages/auth`, not `packages/config` | Same reasoning as the database package (PHASE-0.2 §12): processes that never authenticate anyone should not have to define these. |
| The `AuthStore` port lives in `packages/auth`, implemented in `packages/database` | Keeps cryptography and policy out of the persistence package and SQL out of the auth package (ADR-0011). |
| `users` gained two RLS policies for the runtime role | Unavoidable: authentication precedes tenant context. Constrained to a point lookup plus a column-scoped `last_login_at` update. See §12. |
| A test-only `InMemoryAuthStore` is exported at `@organic-os/auth/testing` | Lets the HTTP layer be tested without a database. Not reachable from the package's main entry point, and its constructor throws under `NODE_ENV=production`. |
| API integration tests duplicate ~35 lines of Testcontainers setup | Exporting it from `@organic-os/database/testing` would put `vitest/node` types into that package's published surface. Both copies must stay in step. |

## 16. Security notes and residual risk

1. **Rate limiting is single-process** (§8). The most significant limitation of the
   phase, tracked for 0.5.
2. **`users` is now readable by the runtime role under an authentication context.**
   Narrowed to a point lookup, but it is a genuinely larger surface than Phase 0.2 had.
   Compensating controls: the policy cannot return more than one row; the context is
   transaction-local and fails closed; only `packages/database/src/auth/store.ts` sets
   it; UPDATE is limited to one column by grant.
3. **`AUTH_SESSION_SECRET` is a new secret to manage.** It keys only the CSRF MAC.
   Rotating it invalidates outstanding CSRF tokens (clients refetch) and does not
   invalidate sessions. It is never logged, never returned, and configuration errors
   report variable names only.
4. **`trustProxy: false`.** Correct today; a proxied deployment must set it explicitly
   or the rate-limit key becomes the proxy's address for every caller.
5. **No audit-log rows for auth events yet.** PHASE-0 §0.3 requires audit writes for
   auth mutations, but `audit_logs` is tenant-scoped and an authentication event has no
   organization at the moment it happens. Resolving that needs the organization
   selection that Phase 0.4 introduces. Authentication events are structured-logged
   today (request id, outcome, coarse reason, user id, session id, source) — see §17.
6. **No account lockout, breach-corpus check, MFA, or password reset.** Out of scope by
   §0.3; MFA and SSO are explicitly post-MVP (SECURITY.md §2).

Nothing is committed that is a secret. `.env.example` gains authentication variables
with clearly labelled local-development-only values.

## 17. Logging

Authentication logs carry: request id, method, url, outcome, coarse failure reason,
user id, session id, source key, and CSRF verdict category.

They never carry: a password, a raw session token, a token hash, a raw CSRF token, a
`Cookie` or `Set-Cookie` header, or the session secret. The observability redaction list
was extended to cover `passwordHash`, `sessionToken`, `tokenHash`, `csrfToken`,
`sessionSecret`, `currentPassword`, `confirmPassword`, `cookies`, `setCookie` and the
bare `headers.*` header locations — a safety net, on top of call sites that log
identifiers rather than payloads. Tests assert the absence of every one of these from
captured log output, over both the unit and the real-PostgreSQL stack.
